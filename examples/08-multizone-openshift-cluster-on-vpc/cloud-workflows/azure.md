# Azure Workflow: Multizone OpenShift / AKS Cluster on VNet

This guide shows the commands and prompts to deploy a multizone managed Kubernetes (AKS) cluster on Azure using IaC Spec Kit. The cluster uses Azure Key Vault for customer-managed key encryption of etcd and node OS disks, Azure Monitor for observability, and Azure Policy for compliance guardrails — aligned to SOC 2 requirements.

> **Note**: The specific files, directory names, and some outputs are generated by the AI and will vary depending on your AI tool (Bob, Claude, Copilot, Gemini, etc.) and the LLM model being used. The workflow structure and file types remain consistent.

## Prerequisites

- Azure subscription with appropriate permissions (AKS, VNet, Key Vault, Storage, Monitor)
- IaC Spec Kit installed (`iac-specify check`)
- Terraform installed (>= 1.9)
- Checkov installed (`pip install checkov`) — for compliance scanning
- AI coding assistant running in your project directory

## Optional: Add Principles First

For long-running projects where you'll incrementally add capabilities (running `/iac.specify` multiple times), establish governance rules BEFORE starting:

```
/iac.principles This is a development environment. Keep it simple, focus on basic security, and keep costs low. Use Terraform. Security and compliance are critical. Multiple environments need strong isolation.
```

**What this does**: Creates or updates `.specify/memory/principles.md` with project-wide governance tenets. The principles file uses semantic versioning and acts as persistent memory across all commands — every subsequent `/iac.plan` and `/iac.implement` will check its decisions against these principles.

For a compliance-scoped cluster like this, expect the principles to establish Enhanced security controls (Key Vault CMK encryption, private endpoints, Azure Policy compliance scanning) for all environments, with cost-conscious node sizing for development.

Principles are project-wide and apply to all features, not just this cluster.

## Commands

### Step 1: Describe What You Want

```
/iac.specify Create a multizone Kubernetes cluster on virtual network having 3 subnets, customer-managed key encryption enabled for etcd and node OS disks, centralized logging, monitoring. Policy-based guardrails to enforce compliance. Cost tracking by environment. We need to comply with SOC 2 requirements.
```

**What this does**: The AI creates a cloud-agnostic infrastructure specification. It makes informed assumptions based on the description and marks any critically ambiguous items with `[NEEDS CLARIFICATION]` (max 3).

**Generates**:
- `spec.md` in a feature directory (directory name is AI-generated based on your description)
- `checklists/requirements.md` for quality validation

**spec.md** contains a cloud-agnostic specification using only generic infrastructure terms. Functional requirements in this example would include:
- Private virtual network with three isolated subnets, one per availability zone
- Managed container orchestration cluster across all three zones (no single zone as single point of failure)
- Encryption of all cluster control-plane data (etcd) at rest using customer-managed keys
- Encryption of all worker node OS disks using customer-managed keys
- Dedicated key management service instance for customer-managed keys
- Centralized log analysis service with retention and search capabilities
- Centralized monitoring service with dashboards and alerting
- Policy-based guardrails evaluating configurations against SOC 2 compliance profiles
- Mandatory cost-tracking tags on every resource
- Full environment isolation: separate virtual network, state backend, key vault, and IAM identities per env
- Private cluster API endpoint
- Least-privilege IAM role assignments

Uses generic terms rather than cloud-specific services (e.g., "key management service" not "Key Vault", "container orchestration" not "AKS"). Specific sections and detail vary by AI tool and LLM model.

### Step 2: Clarify Requirements (Optional)

```
/iac.clarify
```

**What this does**: The AI scans your spec for underspecified areas and asks targeted questions (max 5 per session). Questions are presented with multiple-choice options and the AI recommends answers.

**Updates**: `spec.md` with your answers integrated

**Example questions you might see**:
- "AKS network plugin?" → Options: Azure CNI (recommended for compliance), Kubenet (simpler)
- "Private cluster?" → Options: Private API server endpoint (most secure), Public endpoint with authorized IP ranges
- "Log retention period?" → Options: 30 days, 90 days, 365 days (required for SOC 2)

### Step 3: Create Implementation Plan

**Option A - Minimal**:
```
/iac.plan
```

**Option B - With guidance**:
```
/iac.plan Use East US region. Three-zone deployment.
```

**What this does**: The AI performs lightweight research on current Azure provider and Azure Verified Module versions, then translates the cloud-agnostic spec into an Azure-specific architecture plan. It checks every decision against the principles file.

**Generates**: `plan.md` — complete architecture plan with inline research

**plan.md** contains the main architecture plan including technical context (Azure, Terraform, state backend), principles validation, and infrastructure architecture. For example:
- Cloud: Azure `eastus` (zones 1, 2, 3)
- IaC: Terraform with current stable `hashicorp/azurerm` provider version
- Modules: Azure Verified Modules for AKS, VNet (exact version pins)
- AKS cluster: private API server endpoint, etcd encryption via Key Vault CMK (Disk Encryption Set)
- Node OS disk encryption: Disk Encryption Set linked to Key Vault CMK per environment
- Networking: VNet per environment, 3 node subnets (Azure CNI), 1 management subnet, private endpoints for Key Vault + ACR
- Security: Network Security Groups (node NSG + management NSG), no `0.0.0.0/0` inbound on node subnet
- Observability: Log Analytics Workspace + Container Insights (metrics + logs), 365-day retention
- Compliance: Checkov (preventive CI gate) + Azure Policy (CIS Azure Foundations benchmark, detective)
- State backend: Azure Blob Storage per-env container + Storage Account lock (separate per environment)

**Optional**: For comprehensive documentation, run `/iac.enrichplan` after this step to generate `research.md`, `architecture.md`, `modules.md`, and `quickstart.md`.

### Step 4: Generate Task Breakdown

```
/iac.tasks
```

**What this does**: The AI creates a phased task list organized by infrastructure tiers with clear execution order and parallelization opportunities.

**Generates**: `tasks.md`

**tasks.md** contains an ordered task breakdown organized by tiers. Each task has checkbox format with ID, parallel marker [P], and file path. Example tasks:
- Create resource groups per environment in `iac/resource-groups.tf`
- Create VNet with 3 node subnets + management subnet in `iac/vnet.tf`
- Create Network Security Groups for node and management subnets in `iac/nsg.tf`
- Create Key Vault + CMK + Disk Encryption Set in `iac/kms.tf`
- Create Azure Blob Storage state backend container in `iac/storage.tf`
- Create Log Analytics Workspace + Container Insights solution in `iac/observability.tf`
- Create AKS cluster with private endpoint + Disk Encryption Set in `iac/cluster.tf`
- Configure system + user node pools with OS disk encryption in `iac/cluster.tf`
- Create User-Assigned Managed Identities + RBAC role assignments in `iac/iam.tf`

Specific tasks and organization vary by AI tool and LLM model.

### Step 5: Implement Infrastructure Code

```
/iac.implement
```

**What this does**: The AI executes tasks to generate Terraform `.tf` files, runs formatting and validation, and marks completed tasks.

**Important**: This generates infrastructure code only — it does NOT deploy to Azure (no `terraform apply`).

**Generates**: Terraform configuration files (`.tf` files). Example files might include:
- `backend.tf` (Azure Blob Storage backend, partial config)
- `backend.{dev,staging,prod}.hcl` (per-environment backend configs)
- `provider.tf` (Azure provider config)
- `versions.tf` (Terraform + provider version constraints)
- `variables.tf` (all input variables with validation)
- `terraform.tfvars.{dev,staging,prod}` (per-environment values, no secrets)
- `resource-groups.tf` (Azure resource groups + mandatory tags)
- `iam.tf` (User-Assigned Managed Identities, role assignments)
- `vnet.tf` (VNet, subnets, route tables, private DNS zones)
- `nsg.tf` (Network Security Groups and rules)
- `kms.tf` (Key Vault, CMK, Disk Encryption Set, key rotation)
- `storage.tf` (Storage Account + state backend container)
- `observability.tf` (Log Analytics Workspace, Container Insights, diagnostic settings)
- `cluster.tf` (AKS cluster + node pools + autoscaler + Disk Encryption Set)
- `outputs.tf` (cluster FQDN, VNet ID, subnet IDs, Key Vault URI, etc.)
- `README.md` (bootstrap, init/plan/apply commands, compliance scan guide)

The AI also runs `terraform fmt` and `terraform validate`. Specific files and organization vary by AI tool and LLM model.

**Updates**: `tasks.md` with completed tasks marked as `- [x]`

## What Happens Next

After `/iac.implement` completes, you have compliance-ready Terraform code. The next steps are **manual**:

1. **Bootstrap the Azure Blob Storage state backend** (one-time — see `iac/README.md`)
   ```bash
   az group create --name my-project-tfstate-rg --location eastus
   az storage account create --name myprojectdevtfstate --resource-group my-project-tfstate-rg \
     --sku Standard_LRS --min-tls-version TLS1_2
   az storage container create --name tfstate --account-name myprojectdevtfstate
   ```

2. **Initialize Terraform**
   ```bash
   export ARM_CLIENT_ID="..."
   export ARM_CLIENT_SECRET="..."
   export ARM_SUBSCRIPTION_ID="..."
   export ARM_TENANT_ID="..."
   terraform -chdir=iac init -backend-config=iac/backend.dev.hcl
   ```

3. **Run mandatory compliance scan**
   ```bash
   checkov -d iac/ --framework terraform
   ```

4. **Review the execution plan**
   ```bash
   terraform -chdir=iac plan -var-file=iac/terraform.tfvars.dev
   ```

5. **Deploy to Azure** (creates real resources and incurs costs)
   ```bash
   terraform -chdir=iac apply -var-file=iac/terraform.tfvars.dev
   ```

6. **Retrieve key outputs**
   ```bash
   terraform -chdir=iac output cluster_fqdn
   terraform -chdir=iac output vnet_id
   az aks get-credentials --resource-group my-project-dev --name my-project-dev-cluster
   ```

**Deployment order**: `dev` → `staging` → `prod`. Compliance scan must pass in each environment before promoting.

## Key Points to Remember

- **Directory names are AI-generated**: The AI decides based on your description.
- **Results vary by AI tool**: Different tools may generate slightly different file organizations.
- **Principles are project-wide**: They apply to ALL features, not just this cluster.
- **Principles can be overridden by compliance**: A dev-first baseline may be overridden when the spec requires SOC 2 compliance — Enhanced controls apply to all environments.
- **Specs are technology-agnostic**: Uses generic terms, not Azure-specific services.
- **Plans are Azure-specific**: `plan.md` contains Azure service names, Azure Verified Module sources, and exact version pins.
- **Module versions are exactly pinned**: Modules are NOT captured in `.terraform.lock.hcl` — exact pins (`= X.Y.Z`) are mandatory for reproducibility.
- **State isolation is non-negotiable**: Separate Azure Blob containers per environment (not Terraform workspaces) for compliance-grade isolation.
- **Deployment is manual**: IaC Spec Kit generates code; YOU run `terraform apply` to create actual Azure resources.
- **Cost awareness**: `terraform apply` creates real resources that cost money. Run `infracost breakdown` first.
