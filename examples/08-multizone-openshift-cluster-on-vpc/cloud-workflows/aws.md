# AWS Workflow: Multizone OpenShift / EKS Cluster on VPC

This guide shows the commands and prompts to deploy a multizone managed Kubernetes (EKS) cluster on AWS using IaC Spec Kit. The cluster uses customer-managed KMS keys for etcd and node volume encryption, CloudWatch for observability, and AWS Security Hub for compliance guardrails — aligned to SOC 2 requirements.

> **Note**: The specific files, directory names, and some outputs are generated by the AI and will vary depending on your AI tool (Bob, Claude, Copilot, Gemini, etc.) and the LLM model being used. The workflow structure and file types remain consistent.

## Prerequisites

- AWS account with IAM permissions (EKS, VPC, KMS, S3, CloudWatch, Security Hub)
- IaC Spec Kit installed (`iac-specify check`)
- Terraform installed (>= 1.9)
- Checkov installed (`pip install checkov`) — for compliance scanning
- AI coding assistant running in your project directory

## Optional: Add Principles First

For long-running projects where you'll incrementally add capabilities (running `/iac.specify` multiple times), establish governance rules BEFORE starting:

```
/iac.principles This is a development environment. Keep it simple, focus on basic security, and keep costs low. Use Terraform. Security and compliance are critical. Multiple environments need strong isolation.
```

**What this does**: Creates or updates `.specify/memory/principles.md` with project-wide governance tenets. The principles file uses semantic versioning and acts as persistent memory across all commands — every subsequent `/iac.plan` and `/iac.implement` will check its decisions against these principles.

For a compliance-scoped cluster like this, expect the principles to establish Enhanced security controls (KMS encryption, private endpoints, compliance scanning) for all environments, with cost-conscious sizing for development.

Principles are project-wide and apply to all features, not just this cluster.

## Commands

### Step 1: Describe What You Want

```
/iac.specify Create a multizone Kubernetes cluster on VPC having 3 subnets, KMS encryption enabled for etcd and node volumes, centralized logging, monitoring. Policy-based guardrails to enforce compliance. Cost tracking by environment. We need to comply with SOC 2 requirements.
```

**What this does**: The AI analyzes your description, makes informed assumptions based on industry standards, and creates a detailed infrastructure specification. If anything is critically ambiguous, it will ask up to 3 clarifying questions.

**Generates**:
- `spec.md` in a feature directory (directory name is AI-generated based on your description)
- `checklists/requirements.md` for quality validation

**spec.md** contains a cloud-agnostic specification using only generic infrastructure terms. Functional requirements in this example would include:
- Private virtual network with three isolated subnets, one per availability zone
- Managed container orchestration cluster across all three zones (no single zone as single point of failure)
- Encryption of all cluster control-plane data (etcd) at rest using customer-managed keys
- Encryption of all worker node boot and data volumes using customer-managed keys
- Dedicated key management service instance for customer root keys
- Centralized log analysis service with retention and search capabilities
- Centralized monitoring service with dashboards and alerting
- Policy-based guardrails evaluating configurations against SOC 2 compliance profiles
- Mandatory cost-tracking tags on every resource
- Full environment isolation: separate virtual network, state backend, KMS, and IAM identities per env
- Private-only cluster API endpoints
- Least-privilege IAM roles and policies

Uses generic terms rather than cloud-specific services (e.g., "key management service" not "AWS KMS", "container orchestration" not "EKS"). Specific sections and detail vary by AI tool and LLM model.

---

### Step 2: Clarify Requirements (Optional)

Run structured clarification to resolve any ambiguities before planning.

```
/iac.clarify
```

**What this does**: The AI scans your spec for underspecified areas and asks targeted questions (max 5 per session) about scope, security, cost, or technical details. Questions are presented with multiple-choice options and the AI recommends answers based on your context.

**Updates**: `spec.md` with your answers integrated into the appropriate sections

**Example questions you might see**:
- "Cluster endpoint access?" → Options: Private only (most secure), Public + private (easier access), Public (simplest)
- "Node volume encryption scope?" → Options: Boot volumes only, Boot + data volumes (recommended for compliance)
- "Log retention period?" → Options: 30 days, 90 days, 365 days (required for SOC 2)

You can skip this step if you're confident the spec captures everything.

---

### Step 3: Create Implementation Plan

**Option A - Minimal**:
```
/iac.plan
```

**Option B - With guidance**:
```
/iac.plan Use us-east-1 region. Three-zone deployment.
```

**What this does**: The AI performs lightweight research on current AWS provider and module versions, then translates the cloud-agnostic spec into an AWS-specific architecture plan. It checks every decision against the principles file.

**Generates**: `plan.md` — complete architecture plan with inline research

**plan.md** contains the main architecture plan including technical context (AWS, Terraform, state backend), principles validation, and infrastructure architecture. For example:
- Cloud: AWS `us-east-1` (zones `us-east-1a/b/c`)
- IaC: Terraform with current stable `hashicorp/aws` provider version
- Modules: `terraform-aws-modules/eks/aws`, `terraform-aws-modules/vpc/aws` (exact version pins)
- EKS cluster: private API endpoint, envelope encryption via KMS CMK for etcd secrets
- Worker node groups: managed node groups with EBS volume encryption via KMS CMK
- Networking: VPC per environment with 3 private worker subnets, 3 public subnets for load balancers, NAT Gateways for egress
- Security: Security groups (cluster SG + node SG), no `0.0.0.0/0` inbound on node interfaces
- Observability: CloudWatch Logs (control plane + node logs), CloudWatch Container Insights (metrics)
- Compliance: Checkov (preventive CI gate) + AWS Security Hub with CIS AWS Foundations benchmark (detective)
- State backend: S3 per-env bucket + DynamoDB table for locking, separate per environment

**Optional**: For comprehensive documentation, run `/iac.enrichplan` after this step to generate `research.md`, `architecture.md`, `modules.md`, and `quickstart.md`.

### Step 4: Generate Task Breakdown

Break down the architecture plan into ordered, actionable tasks.

```
/iac.tasks
```

**What this does**: The AI analyzes all planning documents and creates a phased task list that respects infrastructure dependencies. Tasks are organized by tier with clear execution order and parallelization opportunities.

**Generates**: `tasks.md`

**tasks.md** contains an ordered task breakdown organized by tiers. Each task has checkbox format with ID, parallel marker [P], and file path. Example tasks:
- Create VPC with CIDR block, 3 private + 3 public subnets in `iac/vpc.tf`
- Create NAT Gateways (one per zone) in `iac/vpc.tf`
- Create KMS key + key policy for EKS etcd encryption in `iac/kms.tf`
- Create KMS key for EBS node volume encryption in `iac/kms.tf`
- Create S3 state bucket + DynamoDB lock table in `iac/cos.tf`
- Create EKS cluster with private endpoint + KMS envelope encryption in `iac/cluster.tf`
- Configure managed node groups with KMS EBS encryption in `iac/cluster.tf`
- Create CloudWatch log groups + Container Insights in `iac/observability.tf`
- Create IAM roles and least-privilege policies in `iac/iam.tf`

Specific tasks and organization vary by AI tool and LLM model.

---

### Step 5: Implement Infrastructure Code

Execute all tasks to generate the Terraform configuration files.

```
/iac.implement
```

**What this does**: The AI reads `tasks.md` and executes each task in order, respecting dependencies and parallelization markers. It generates Terraform `.tf` files following AWS and Terraform best practices, runs formatting and validation, and marks completed tasks as `[x]` in `tasks.md`.

**Important**: This command generates infrastructure code only — it does NOT deploy to AWS (no `terraform apply`). Deployment is a manual step you control.

**Generates**: Terraform configuration files (`.tf` files). Example files might include:
- `backend.tf` (S3 + DynamoDB state backend, partial config)
- `backend.{dev,staging,prod}.hcl` (per-environment backend configs)
- `provider.tf` (AWS provider config)
- `versions.tf` (Terraform + provider version constraints)
- `variables.tf` (all input variables with validation)
- `terraform.tfvars.{dev,staging,prod}` (per-environment values, no secrets)
- `resource-groups.tf` (AWS resource tagging defaults)
- `iam.tf` (IAM roles, policies, instance profiles)
- `vpc.tf` (VPC, subnets, NAT Gateways, Internet Gateway, route tables)
- `security-groups.tf` (cluster SG + node SG with explicit rules)
- `kms.tf` (KMS CMKs for etcd and EBS, key policies, rotation)
- `cluster.tf` (EKS cluster + managed node groups + autoscaler)
- `observability.tf` (CloudWatch log groups, Container Insights, alarms)
- `outputs.tf` (cluster endpoint, VPC ID, subnet IDs, KMS key ARNs, etc.)
- `README.md` (bootstrap, init/plan/apply commands, compliance scan guide)

**Updates**: `tasks.md` with completed tasks marked as `- [x]`

## What Happens Next

After `/iac.implement` completes, you have compliance-ready Terraform code. The next steps are **manual** and outside the scope of IaC Spec Kit:

1. **Bootstrap the S3 state bucket and DynamoDB table** (one-time — see `iac/README.md`)
   ```bash
   aws s3 mb s3://my-project-dev-tfstate --region us-east-1
   aws dynamodb create-table --table-name my-project-dev-tflock \
     --attribute-definitions AttributeName=LockID,AttributeType=S \
     --key-schema AttributeName=LockID,KeyType=HASH \
     --billing-mode PAY_PER_REQUEST --region us-east-1
   ```

2. **Initialize Terraform**
   ```bash
   export AWS_ACCESS_KEY_ID="..."
   export AWS_SECRET_ACCESS_KEY="..."
   terraform -chdir=iac init -backend-config=iac/backend.dev.hcl
   ```

3. **Run mandatory compliance scan**
   ```bash
   checkov -d iac/ --framework terraform
   ```

4. **Review the execution plan**
   ```bash
   terraform -chdir=iac plan -var-file=iac/terraform.tfvars.dev
   ```

5. **Deploy to AWS** (creates real resources and incurs costs)
   ```bash
   terraform -chdir=iac apply -var-file=iac/terraform.tfvars.dev
   ```

6. **Retrieve key outputs**
   ```bash
   terraform -chdir=iac output cluster_endpoint
   terraform -chdir=iac output vpc_id
   aws eks update-kubeconfig --name my-project-dev-cluster --region us-east-1
   ```

**Deployment order**: `dev` → `staging` → `prod`. Compliance scan must pass in each environment before promoting.

## Key Points to Remember

- **Directory names are AI-generated**: Don't expect specific names. The AI decides based on your description.
- **Results vary by AI tool**: Claude, Copilot, Gemini may generate slightly different file organizations.
- **Principles are project-wide**: They apply to ALL features you build, not just this cluster.
- **Principles can be overridden by compliance**: A dev-first baseline in principles may be overridden when the spec requires SOC 2 compliance — Enhanced controls apply to all environments.
- **Specs are technology-agnostic**: No AWS-specific terms in `spec.md`.
- **Plans are AWS-specific**: `plan.md` contains AWS service names, `terraform-aws-modules` sources, and exact version pins.
- **Module versions are exactly pinned**: Modules are NOT captured in `.terraform.lock.hcl` — exact pins (`= X.Y.Z`) are mandatory for reproducibility.
- **State isolation is non-negotiable**: Separate S3 buckets + DynamoDB tables per environment (not Terraform workspaces) for compliance-grade isolation.
- **Deployment is manual**: IaC Spec Kit generates code; YOU run `terraform apply` to create actual AWS resources.
- **Cost awareness**: Running `terraform apply` creates real AWS resources that cost money. Run `infracost breakdown` first.
