# GCP Workflow: Multizone OpenShift / GKE Cluster on VPC Network

This guide shows the commands and prompts to deploy a multizone managed Kubernetes (GKE) cluster on Google Cloud Platform using IaC Spec Kit. The cluster uses Cloud KMS for customer-managed key encryption of etcd and node boot disks, Cloud Logging and Cloud Monitoring for observability, and Org Policy / Security Command Center for compliance guardrails — aligned to SOC 2 requirements.

> **Note**: The specific files, directory names, and some outputs are generated by the AI and will vary depending on your AI tool (Bob, Claude, Copilot, Gemini, etc.) and the LLM model being used. The workflow structure and file types remain consistent.

## Prerequisites

- GCP project with billing enabled and appropriate IAM permissions (GKE, VPC, KMS, GCS, Logging, Monitoring)
- IaC Spec Kit installed (`iac-specify check`)
- Terraform installed (>= 1.9)
- Checkov installed (`pip install checkov`) — for compliance scanning
- AI coding assistant running in your project directory

## Optional: Add Principles First

For long-running projects where you'll incrementally add capabilities (running `/iac.specify` multiple times), establish governance rules BEFORE starting:

```
/iac.principles This is a development environment. Keep it simple, focus on basic security, and keep costs low. Use Terraform. Security and compliance are critical. Multiple environments need strong isolation.
```

**What this does**: Creates or updates `.specify/memory/principles.md` with project-wide governance tenets. The principles file uses semantic versioning and acts as persistent memory across all commands — every subsequent `/iac.plan` and `/iac.implement` will check its decisions against these principles.

For a compliance-scoped cluster like this, expect the principles to establish Enhanced security controls (Cloud KMS encryption, private endpoint, Org Policy guardrails) for all environments, with cost-conscious node sizing and preemptible/Spot nodes for development.

Principles are project-wide and apply to all features, not just this cluster.

## Commands

### Step 1: Describe What You Want

```
/iac.specify Create a multizone Kubernetes cluster on virtual network having 3 subnets, customer-managed key encryption enabled for etcd and node boot disks, centralized logging, monitoring. Policy-based guardrails to enforce compliance. Cost tracking by environment. We need to comply with SOC 2 requirements.
```

**What this does**: The AI creates a cloud-agnostic infrastructure specification. It makes informed assumptions based on the description and marks any critically ambiguous items with `[NEEDS CLARIFICATION]` (max 3).

**Generates**:
- `spec.md` in a feature directory (directory name is AI-generated based on your description)
- `checklists/requirements.md` for quality validation

**spec.md** contains a cloud-agnostic specification using only generic infrastructure terms. Functional requirements in this example would include:
- Private virtual network with three isolated subnets, one per availability zone
- Managed container orchestration cluster across all three zones (no single zone as single point of failure)
- Encryption of all cluster control-plane data (etcd) at rest using customer-managed keys
- Encryption of all worker node boot disks using customer-managed keys
- Dedicated key management service instance for customer-managed keys
- Centralized log analysis service with retention and search capabilities
- Centralized monitoring service with dashboards and alerting
- Policy-based guardrails evaluating configurations against SOC 2 compliance profiles
- Mandatory cost-tracking labels on every resource
- Full environment isolation: separate virtual network, state backend, KMS key ring, and service accounts per env
- Private cluster endpoint (no public API server)
- Least-privilege IAM service accounts with Workload Identity

Uses generic terms rather than cloud-specific services (e.g., "key management service" not "Cloud KMS", "container orchestration" not "GKE"). Specific sections and detail vary by AI tool and LLM model.

### Step 2: Clarify Requirements (Optional)

```
/iac.clarify
```

**What this does**: The AI scans your spec for underspecified areas and asks targeted questions (max 5 per session). Questions are presented with multiple-choice options and the AI recommends answers.

**Updates**: `spec.md` with your answers integrated

**Example questions you might see**:
- "GKE cluster mode?" → Options: Autopilot (less operational overhead), Standard (more control)
- "Private cluster endpoint?" → Options: Private nodes + private master (most secure), Private nodes + public master with authorized networks
- "Node cost optimization?" → Options: Standard VMs, Spot/Preemptible VMs for dev (significant cost reduction)
- "Log retention period?" → Options: 30 days, 90 days, 365 days (required for SOC 2)

### Step 3: Create Implementation Plan

**Option A - Minimal**:
```
/iac.plan
```

**Option B - With guidance**:
```
/iac.plan Use us-central1 region. Three-zone deployment.
```

**What this does**: The AI performs lightweight research on current GCP provider and `terraform-google-modules` versions, then translates the cloud-agnostic spec into a GCP-specific architecture plan. It checks every decision against the principles file.

**Generates**: `plan.md` — complete architecture plan with inline research

**plan.md** contains the main architecture plan including technical context (GCP, Terraform, state backend), principles validation, and infrastructure architecture. For example:
- Cloud: GCP `us-central1` (zones `a`, `b`, `c`)
- IaC: Terraform with current stable `hashicorp/google` provider version
- Modules: `terraform-google-modules/kubernetes-engine/google`, `terraform-google-modules/network/google` (exact version pins)
- GKE Standard cluster: private nodes + private master endpoint, etcd encryption via Cloud KMS CMEK
- Node pool boot disk encryption: Cloud KMS key ring + CryptoKey per environment
- Networking: Shared VPC or project-level VPC per environment, 3 node subnets (one per zone), Private Google Access enabled, Cloud NAT for egress, no public node IPs
- Security: Firewall rules (node firewall + master-authorized-networks), Workload Identity for pod IAM, Binary Authorization
- Observability: Cloud Logging (system + workload logs), Cloud Monitoring (GKE metrics + custom dashboards)
- Compliance: Checkov (preventive CI gate) + Security Command Center (CIS GCP Foundations benchmark, detective)
- State backend: GCS per-env bucket with versioning + uniform bucket-level access (separate per environment)

**Optional**: For comprehensive documentation, run `/iac.enrichplan` after this step to generate `research.md`, `architecture.md`, `modules.md`, and `quickstart.md`.

### Step 4: Generate Task Breakdown

```
/iac.tasks
```

**What this does**: The AI creates a phased task list organized by infrastructure tiers with clear execution order and parallelization opportunities.

**Generates**: `tasks.md`

**tasks.md** contains an ordered task breakdown organized by tiers. Each task has checkbox format with ID, parallel marker [P], and file path. Example tasks:
- Create VPC Network with 3 node subnets (private, secondary ranges for pods/services) in `iac/vpc.tf`
- Configure Cloud NAT + Cloud Router for node egress in `iac/vpc.tf`
- Create Cloud KMS key ring + CryptoKey per environment in `iac/kms.tf`
- Create IAM service accounts + Workload Identity bindings in `iac/iam.tf`
- Create GCS state bucket with versioning + uniform access in `iac/storage.tf`
- Create GKE cluster with private endpoint + CMEK encryption in `iac/cluster.tf`
- Configure default node pool with boot disk encryption + Spot VMs (dev) in `iac/cluster.tf`
- Create Cloud Logging sinks + Cloud Monitoring alert policies in `iac/observability.tf`

Specific tasks and organization vary by AI tool and LLM model.

### Step 6: Implement Infrastructure Code

```
/iac.implement
```

**What this does**: The AI executes tasks to generate Terraform `.tf` files, runs formatting and validation, and marks completed tasks.

**Important**: This generates infrastructure code only — it does NOT deploy to GCP (no `terraform apply`).

**Generates**: Terraform configuration files (`.tf` files). Example files might include:
- `backend.tf` (GCS backend, partial config)
- `backend.{dev,staging,prod}.hcl` (per-environment backend configs)
- `provider.tf` (GCP provider config with Workload Identity Federation or service account key reference)
- `versions.tf` (Terraform + provider version constraints)
- `variables.tf` (all input variables with validation)
- `terraform.tfvars.{dev,staging,prod}` (per-environment values, no secrets)
- `iam.tf` (service accounts, IAM bindings, Workload Identity)
- `vpc.tf` (VPC Network, subnets with secondary ranges, Cloud NAT, Cloud Router)
- `firewall.tf` (firewall rules for node + master-authorized-networks)
- `kms.tf` (Cloud KMS key ring, CryptoKey, rotation schedule, IAM binding for GKE)
- `storage.tf` (GCS state bucket with versioning + lifecycle)
- `observability.tf` (Cloud Logging sinks, Cloud Monitoring alert policies, dashboards)
- `cluster.tf` (GKE cluster + node pools + autoscaler + CMEK + Workload Identity)
- `outputs.tf` (cluster endpoint, VPC name, subnet IDs, KMS key ID, etc.)
- `README.md` (bootstrap, init/plan/apply commands, compliance scan guide)

The AI also runs `terraform fmt` and `terraform validate`. Specific files and organization vary by AI tool and LLM model.

**Updates**: `tasks.md` with completed tasks marked as `- [x]`

## What Happens Next

After `/iac.implement` completes, you have compliance-ready Terraform code. The next steps are **manual**:

1. **Bootstrap the GCS state bucket** (one-time — see `iac/README.md`)
   ```bash
   gcloud storage buckets create gs://my-project-dev-tfstate \
     --location=us-central1 --uniform-bucket-level-access
   gcloud storage buckets update gs://my-project-dev-tfstate --versioning
   ```

2. **Initialize Terraform**
   ```bash
   export GOOGLE_APPLICATION_CREDENTIALS="/path/to/sa-key.json"
   # Or use: gcloud auth application-default login
   terraform -chdir=iac init -backend-config=iac/backend.dev.hcl
   ```

3. **Run mandatory compliance scan**
   ```bash
   checkov -d iac/ --framework terraform
   ```

4. **Review the execution plan**
   ```bash
   terraform -chdir=iac plan -var-file=iac/terraform.tfvars.dev
   ```

5. **Deploy to GCP** (creates real resources and incurs costs)
   ```bash
   terraform -chdir=iac apply -var-file=iac/terraform.tfvars.dev
   ```

6. **Retrieve key outputs and connect**
   ```bash
   terraform -chdir=iac output cluster_endpoint
   gcloud container clusters get-credentials my-project-dev-cluster \
     --region us-central1 --project my-gcp-project
   ```

**Deployment order**: `dev` → `staging` → `prod`. Compliance scan must pass in each environment before promoting.

## Key Points to Remember

- **Directory names are AI-generated**: The AI decides based on your description.
- **Results vary by AI tool**: Different tools may generate slightly different file organizations.
- **Principles are project-wide**: They apply to ALL features, not just this cluster.
- **Principles can be overridden by compliance**: A dev-first baseline may be overridden when the spec requires SOC 2 compliance — Enhanced controls apply to all environments.
- **Specs are technology-agnostic**: Uses generic terms, not GCP-specific services.
- **Plans are GCP-specific**: `plan.md` contains GCP service names, `terraform-google-modules` sources, and exact version pins.
- **Module versions are exactly pinned**: Modules are NOT captured in `.terraform.lock.hcl` — exact pins (`= X.Y.Z`) are mandatory for reproducibility.
- **State isolation is non-negotiable**: Separate GCS buckets per environment (not Terraform workspaces) for compliance-grade isolation.
- **Deployment is manual**: IaC Spec Kit generates code; YOU run `terraform apply` to create actual GCP resources.
- **Cost awareness**: `terraform apply` creates real GCP resources that cost money. Run `infracost breakdown` first.
