# IBM Cloud Workflow: Multizone OpenShift Cluster on VPC

This guide shows the commands and prompts used to deploy a multizone Red Hat OpenShift (ROKS) cluster on IBM Cloud VPC using IaC Spec Kit. The cluster is encrypted with customer-managed keys, integrated with IBM Cloud Logs and Monitoring, and hardened to SOC 2 Type II and IBM Financial Services Cloud (FSCloud) standards.

> **Note**: The specific files, directory names, and some outputs are generated by the AI and will vary depending on your AI tool (Bob, Claude, Copilot, Gemini, etc.) and the LLM model being used. The workflow structure and file types remain consistent.

## Prerequisites

- IBM Cloud account with Pay-As-You-Go plan and sufficient quota for VPC, ROKS, Key Protect, COS, Logs, and Monitoring
- IaC Spec Kit installed (`iac-specify check`)
- Terraform installed (>= 1.9)
- Checkov installed (`pip install checkov`) — required for FSCloud compliance scanning
- AI coding assistant running in your project directory

## Optional: Add Principles First

For long-running projects where you'll incrementally add capabilities (running `/iac.specify` multiple times), establish governance rules BEFORE starting:

```
/iac.principles This is a development environment. Keep it simple, focus on basic security, and keep costs low. Use Terraform. Security and compliance are critical. Multiple environments need strong isolation.
```

**What this does**: Creates or updates `.specify/memory/principles.md` with project-wide governance tenets. The principles file uses semantic versioning and acts as persistent memory across all commands — every subsequent `/iac.plan` and `/iac.implement` will check its decisions against these principles.

**In this example**, the principles output was **v2.0.0** (MAJOR bump), reflecting:
- Dev-first, cost-conscious baseline with `bx2.4x16` workers and autoscaler off in dev
- Enhanced security controls (KMS, private endpoints, Checkov FSCloud scan) for ALL environments because compliance requirements override the dev-first posture
- Non-negotiable environment isolation: separate VPC, Key Protect instance, state backend, and IAM service ID per environment
- Progressive complexity: "Simple" is the default starting point; "Organised" justified here due to 6+ resource types and 3 environments

Principles are project-wide and apply to all features, not just this cluster.

## Commands

### Step 1: Describe What You Want

```
/iac.specify Create a multizone Red Hat OpenShift cluster on VPC having 3 subnets, KMS encryption enabled for etcd and worker volumes, Log Analysis, Monitoring. Policy-based guardrails to enforce compliance. Cost tracking by environment. We need to comply with SOC 2 and Financial Services Cloud requirements.
```

**What this does**: The AI creates a cloud-agnostic infrastructure specification. It makes informed assumptions based on the description and marks any critically ambiguous items with `[NEEDS CLARIFICATION]` (max 3).

**Generates**:
- `specs/001-ocp-cluster/spec.md` — cloud-agnostic requirements
- `specs/001-ocp-cluster/checklists/requirements.md` — 17-item quality validation checklist (all passed)

**spec.md** contains a cloud-agnostic specification using only generic infrastructure terms. Functional requirements in this example included:
- Private virtual network with three isolated subnets, one per availability zone
- Managed container orchestration cluster across all three zones (no single zone as single point of failure)
- Encryption of all cluster control-plane data (etcd) at rest using customer-managed keys
- Encryption of all worker node boot and data volumes using customer-managed keys
- Dedicated key management service instance for customer root keys
- Centralized log analysis service (platform and worker node logs, 365-day retention)
- Centralized monitoring service with dashboards and alerting
- Policy-based guardrails evaluating configurations against SOC 2 and FSCloud compliance profiles
- Mandatory cost-tracking tags on every resource (`environment`, `project`, `team`, `cost-center`)
- Full environment isolation: separate virtual network, state backend, KMS, and IAM identities per env
- Private-only cluster endpoints — no public access to cluster components
- Least-privilege IAM roles and policies

Uses generic terms rather than cloud-specific services (e.g., "key management service" not "Key Protect", "container orchestration" not "ROKS"). Specific sections and detail vary by AI tool and LLM model.

### Step 3: Create Implementation Plan

**Option A - Minimal**:
```
/iac.plan
```

**Option B - With guidance**:
```
/iac.plan Use us-south region. Three-zone deployment.
```

**What this does**: The AI performs lightweight research on current IBM Cloud provider and module versions, then translates the cloud-agnostic spec into an IBM Cloud-specific architecture plan. It checks every decision against the principles file.

**Generates**: `specs/001-ocp-cluster/plan.md` — complete architecture plan with inline research

**plan.md** in this example included:

*Technical Context*:
- Cloud: IBM Cloud `us-south` (zones `us-south-1/2/3`)
- IaC: Terraform `>= 1.9, < 2.0` (researched current stable: v1.16.2)
- IBM Provider: `ibm-cloud/ibm >= 2.4.0, < 3.0.0` (current: v2.6.1)
- All 6 `terraform-ibm-modules` pinned to exact versions (`= X.Y.Z`):
  - `terraform-ibm-modules/base-ocp-vpc/ibm = 3.91.2` (ROKS cluster)
  - `terraform-ibm-modules/key-protect/ibm = 2.13.6`
  - `terraform-ibm-modules/observability-instances/ibm = 3.5.3`
  - `terraform-ibm-modules/vpc/ibm = 1.7.0`
  - `terraform-ibm-modules/cos/ibm = 10.17.11`
  - `terraform-ibm-modules/resource-group/ibm = 1.6.1`

*Principles Check*: All 7 principles satisfied with documented justifications.

*Infrastructure Architecture*:
- ROKS cluster: private-only endpoint, etcd encryption via `kms_config`, worker disk encryption via `boot_volume_encryption_kms_config`
- Per-environment worker flavors: `bx2.4x16` (dev, 1/zone) → `bx2.8x32` (staging, 2/zone) → `bx2.16x64` (prod, 3/zone)
- Networking: VPC per env (`10.10/20/30.0.0/16`), 3 × `/24` worker subnets, public gateways for egress, cluster + worker security groups (no `0.0.0.0/0` inbound)
- Network ACLs: default-deny with explicit allow rules at subnet level
- KMS: one Key Protect instance + one CRK per environment, 365-day auto-rotation
- State backend: COS per-env bucket, separate `-backend-config` `.hcl` files (not workspaces)
- Compliance: Checkov FSCloud profile (preventive CI gate) + IBM SCC daily scans (detective)

*Complexity*: Organised structure justified (6 resource types, 3 environments, compliance scanning)

**Optional**: For comprehensive documentation, run `/iac.enrichplan` after this step to generate `research.md`, `architecture.md`, `modules.md`, and `quickstart.md`.

## What Happens Next

After `/iac.implement` completes, you have compliance-ready Terraform code. The next steps are **manual**:

1. **Bootstrap the COS state bucket** (one-time — see `iac/README.md`)
   ```bash
   ibmcloud resource service-instance-create ocp-cluster-dev-cos cloud-object-storage standard global
   ibmcloud cos bucket-create --bucket ocp-cluster-dev-tfstate --region us-south \
     --ibm-service-instance-id $(ibmcloud resource service-instance ocp-cluster-dev-cos --id --quiet)
   ```

2. **Fill in backend credentials** — update `iac/backend.dev.hcl` with the COS instance CRN

3. **Initialize Terraform**
   ```bash
   export TF_VAR_ibmcloud_api_key="<your-api-key>"
   terraform -chdir=iac init -backend-config=iac/backend.dev.hcl
   ```

4. **Run mandatory compliance scan** (required before any merge)
   ```bash
   checkov -d iac/ --framework terraform --check CKV_IBM_*
   ```

5. **Review the execution plan**
   ```bash
   terraform -chdir=iac plan -var-file=iac/terraform.tfvars.dev
   ```

6. **Deploy to IBM Cloud** (creates real resources and incurs costs)
   ```bash
   terraform -chdir=iac apply -var-file=iac/terraform.tfvars.dev
   ```

7. **Retrieve key outputs**
   ```bash
   terraform -chdir=iac output cluster_id
   terraform -chdir=iac output vpc_id
   terraform -chdir=iac output kp_instance_crn
   terraform -chdir=iac output -json cluster_api_endpoint  # sensitive
   ```

**Deployment order**: `dev` → `staging` → `prod`. Checkov scan + SCC baseline report must pass in each environment before promoting to the next.

## Key Points to Remember

- **Directory names are AI-generated**: The branch and spec directory (`001-ocp-cluster`) were auto-detected from the existing git branch.
- **Results vary by AI tool**: Different tools may generate slightly different file organizations and module choices.
- **Principles are project-wide**: They apply to ALL features in the project, not just this cluster. The v2.0.0 principles established here will govern future `/iac.specify` runs.
- **Principles can be overridden by compliance**: This example showed principles v2.0.0 setting a dev-first baseline, but the SOC 2 + FSCloud compliance requirement in the spec explicitly elected Enhanced controls for all environments — including dev.
- **Specs are technology-agnostic**: `spec.md` uses generic terms; no IBM Cloud service names appear until `plan.md`.
- **Plans are IBM Cloud-specific**: `plan.md` contains IBM Cloud service names, `terraform-ibm-modules` sources, and exact version pins.
- **Module versions are exactly pinned**: Modules are NOT captured in `.terraform.lock.hcl` — exact pins (`= X.Y.Z`) are mandatory for reproducibility.
- **State isolation is non-negotiable**: Separate COS buckets + separate backend `.hcl` files per environment (not Terraform workspaces) to satisfy FSCloud isolation requirements.
- **Deployment is manual**: IaC Spec Kit generates code; YOU run `terraform apply` to create actual IBM Cloud resources.
- **Cost awareness**: `terraform apply` creates real resources that cost money. Run `infracost breakdown` first.
